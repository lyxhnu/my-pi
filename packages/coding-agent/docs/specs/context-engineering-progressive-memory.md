# 短期记忆：Shake → Compaction → 模型决策换窗

状态：已实现；确定性回归、独立 CLI/RPC 用户流程和真实模型测试详见验收记录。日期：2026-09-16。

需求：本地裁剪、语义压缩、模型自主决定是否硬切窗口；换窗前保存 Note，新窗口结合 Note 与 Todo 继续同一任务。

本实现基于当前工作区（包括已有未提交修改）。本文定义现行渐进维护契约，替代历史 Spec 中容量事件直接触发换窗的流程。

## 1. 核心决策

采用一个固定的上下文维护流程：**运行时负责容量，模型负责是否换窗，Session 负责状态持久化。**

- Shake：确定性卸载工作上下文中的大块历史内容，不调用模型。
- Compaction：将较早历史压缩为摘要，保留当前工作集；仍属于同一个窗口。
- 硬切窗口：模型显式调用 `new_context`，保存并验证 Note/Todo 后，清空旧窗口的工作历史，通过恢复入口继续任务。

这里的渐进顺序约束**容量压力触发的维护**。模型也可以在任务自然断点主动请求换窗；这种显式请求直接进入同一保存和提交流程，不强制再支付一次不必要的摘要调用。两类入口共享同一个换窗执行流程。

模型的自主权不包含突破模型容量：没有有效换窗意图且请求无法安全发送时，运行时停止该次执行，记录未完成原因，不自行换窗。

## 2. 实现变化

| 原实现 | 已实现的变化 |
| --- | --- |
| 工具回合后已有自动 Shake，但触发基于消息估算；最终预算守卫另行判断 | 维护与发送共同使用完成 transform、消息转换、append-only 组装后的最终请求预算 |
| `AgentSession.compact()` 主要服务手动 `/compact` | 提取共享摘要操作，接入自动压力流程；自动路径不调用会 abort 当前运行的手动入口 |
| 达到工作预算或 provider 拒绝容量，可直接进入保存和自动 rollover | 容量事件只触发减负与决策提示；只有模型持久化的 `new_context` 意图授权硬切 |
| Compaction entry 会建立新 windowId | Compaction 只更新上下文内容修订；硬切才创建新的窗口身份 |
| 新窗以 `resume_ref` 启动，按模型选择的引用恢复 | 复用按需恢复；运行时保证未完成 Todo 不因模型漏选而消失 |
| Todo 工具先改内存、后持久化 | 先生成候选快照，持久化成功后再发布内存状态 |

现行“默认不注入全部 Todo/Note”的设计不等于缺陷。本次强化的是未完成任务的恢复覆盖，不要求首请求整包加载历史。

## 3. 单一维护流程

```text
准备下一次真实请求 → 测量预算
  ├─ 工作预算充足 → 执行业务
  └─ 有容量压力
       → Shake → 重建并测量
           ├─ 工作预算恢复 → 执行业务
           └─ Compaction → 验证候选请求 → 提交 → 重建并测量
                ├─ 工作预算恢复 → 执行业务
                └─ 模型决策
                     ├─ 留在当前窗 → 仅在实际业务预算允许时继续
                     └─ new_context
                          → 保存 Note / 同步 Todo
                          → 校验并提交换窗
                          → 恢复任务要求、Note、Todo
                          → 继续业务
```

模型主动调用 `new_context` 从“保存 Note / 同步 Todo”进入。保存时先同步 Todo，再最后写入或确认 `next_action/current`；保存可以提前完成，但提交前必须检查它对当前状态是否仍有效，不强制重复写相同笔记。

### 3.1 预算与触发

每次实际请求均满足：

```text
I + R + S <= W
工作输入上限 B = min(p × W, W - R - S) - H
```

- `I`：最终实际请求全部输入的估算，包括 system、工具定义、投影、图片及本次交付消息；适用时由 provider usage 锚定，不宣称是精确 tokenizer 计数。
- `R`：本次请求输出预留；`S`：安全余量；`W`：模型窗口。
- `p`：维护触发比例，初始沿用当前 85%，不为三个阶段另设一组百分比。
- `H`：决策和状态保存的新增输入空间；与输出预留分开记账。

现有保存阶段的 2048 输出 token、3072 控制 token、最多 3 次 sampling 可作为初始额度，必须覆盖 Todo 更新与返回内容并重新验证。数值不是“必定保存成功”的保证。所有摘要、决策、保存和恢复请求都独立检查自己的完整预算。

`get_context_remaining` 使用同一份预算快照，返回测量点与当前维护阶段。未知预算继续标记 unknown，不能视为已有可用空间。最终发送前必须重新校验，不能用上次工具查询值授权发送。

每个来源上下文修订至多执行一次 Shake、一次自动 Compaction 操作。没有新增业务内容时，不因阶段切换、查询或提示消息重新获得压缩机会；状态与已消耗额度须可从 Session 恢复。预算恢复后才回到业务阶段。

### 3.2 Shake：移出正文，保留可定位来源

复用现有 region/redaction 实现及 Session 重放，只处理已完整持久化、允许卸载的历史工具输出和大块内容。

自动 Shake 必须保护当前有效用户要求、当前必读 Note/Todo、未完成工具批次及最近工作集。代码块或 XML 的外观本身不是“可以删除用户要求”的依据。工具调用与结果的关联结构必须完整。

替换正文保留来源引用；原始日志不改写。只有 History 实际允许读取的内容才承诺可回读。完成后按真实请求重算预算，不以估计的 `tokensSaved` 代替验证。

### 3.3 Compaction：同窗语义压缩

复用现有 `prepareCompaction` 和摘要生成能力，提取内部的“准备、生成、校验、提交”操作，供自动维护和手动入口共同使用。自动操作在 Agent loop 已退出且整批工具结果落盘的位置执行。

压缩对象是较早的历史前缀，保留当前目标、生效要求、当前 Note/Todo 工作集及最近完整工具交互。摘要记录重要发现、决策、已完成工作、失败事实和来源引用，不将推测升级为事实。

摘要是当前窗口的历史表示，Note 是跨窗续跑的语义记录，Todo 是任务状态；三者职责不同。Compaction 不修改 Todo 状态、不自动写 Note、不把摘要变成新的用户授权。生成 Note 时，摘要可以提供线索，关键结论仍须引用权威来源。

候选摘要提交前必须满足：输出完整且非空、来源修订未变、切点不拆工具交互、完整候选请求严格变小。符合条件但仍有压力时，进入模型决策，不能对同一来源反复“摘要的摘要”。摘要生成请求本身也必须容纳全部待处理材料；不能靠静默截断生效要求通过预算。

没有可压缩范围、候选没有净减少或未能产出有效摘要时，保持原状态，在预算允许的前提下进入同一模型决策阶段；不新增 Rescue Shake、备用模型或另一套降级流程。取消和显式扩展 veto 终止本次维护，不绕过它们继续切窗。

### 3.4 模型决策与保存

模型得到当前预算、Shake/Compaction 结果以及现有任务状态，判断剩余工作是否适合留在当前窗口。

- 不调用 `new_context`：表示没有换窗授权。正常业务仍受工作预算约束；不足时允许有界的整理或最终回答，不能开始新的业务操作。
- 调用 `new_context({reason})`：持久化换窗意图；工具返回 requested，不立即清空消息。
- 模型完成任务：正常结束，不为了维护上下文再启动一次业务续跑。

受限整理阶段开放 `history`、`context_note`、`todo_write`、`get_context_remaining`、`new_context`，仍遵守工具权限。`todo_write` 仅用于同步真实进度，不能为腾出空间删除未完成任务。不能仅因 Note 合法或 Todo 未完成就自动推导换窗授权。

一批并行工具包含 `new_context` 时，必须等全部已接受工具结束并持久化；其他工具改变事实后重新验证 Note。存在未完成 Task 或待审批操作时延后提交。用户取消立即停止后续阶段。

若一次巨大输入或工具结果越过了保存空间，仍先检查可执行的 Shake/Compaction；其后决策或保存请求无法通过预算时，明确停止。不得伪造 Note、跳过保存或擅自切窗。该情况是容量约束下的终态，不是另一条恢复策略。

## 4. Note、Todo 与恢复材料

沿用当前追加式 Session：原始消息/工具结果、`task-note-event` 和 `todo-state` 是既有记录，不另建 handoff 文件或第二套状态账本。

| 材料 | 负责的内容 | 不能代替的内容 |
| --- | --- | --- |
| 用户要求及 Task contract | 目标、范围、约束、验收要求 | 不由摘要或 Note 覆盖 |
| Note | 关键约束引用、决策、当前事实、失败尝试、下一动作与依赖来源 | 不能自行宣布任务完成 |
| Todo | 稳定 ID、内容、pending/in_progress/completed/cancelled | 不能靠 Note 中的自然语言重新推断状态 |
| History | 可回读的原始消息与执行证据 | 历史成功不自动证明当前仍成功 |

保留现有 Note kinds 与 supersedes/retract 机制。换窗前必须存在有效 `next_action/current`：明确下一项动作，关联 Todo ID、所需 Note 与证据引用；目标及要求引用可解析。已变化或无法核对的证据标为 stale/unknown，不承诺语义无损。

恢复清单中的未完成 Todo 集合由运行时从当前分支的最新 `todo-state` 计算，覆盖全部 pending/in_progress，不受模型 `resume.todoIds` 当前 8 项上限约束，也不把全部任务塞入该依赖字段。已完成和已取消条目只在下一动作依赖时读取。没有 Todo 的简单任务允许空集合，不为了换窗制造任务。

Todo 更新使用“生成候选 → 持久化 → 发布内存”的单一提交点。Note 与 Todo 可以分别保存，但 rollover 必须绑定并校验二者的确定版本；途中取消只留下已成功保存的状态，不留下半完成换窗。

## 5. 硬切与新窗口续跑

复用 `ContextRolloverCoordinator` 的 PreparedContinuation、版本校验、提交和 dispatch 协议：

1. 确认来自当前窗口和任务的模型换窗意图；校验工具批次完整。
2. 固定恢复引用：用户要求、有效 Note、完整未完成 Todo 集合、历史截止位置，以及相关来源修订。
3. 构造目标窗口请求，并预检恢复工作集、完整业务工具定义、正常输出和下一轮保存空间。
4. 提交前复核 Session、Note、Todo、队列、工具配置等修订；变化后重组并重新验证，沿用现有最多一次重组限制。
5. 原子追加 rollover；这是唯一换窗提交点。随后发送预检过的同一个 PreparedContinuation。
6. 新窗通过 `resume_ref` 读取当前有效用户要求、必需 Note、全部未完成 Todo；长内容分页。恢复材料进入实际模型请求后，才开放依赖它们的业务执行。
7. 从 Note 的下一动作继续，并依据 Todo 推进；沿用同一任务身份、promptGeneration、授权和队列交付规则。

恢复读取与业务工具出现在同一批时，业务工具仍不得执行：模型还未看到本批读取结果。恢复收据必须对应最终实际请求中仍存在的材料，不能仅以“此前查询过”认定完成。

新窗首请求继续使用现有小型 bootstrap。恢复后的有效业务上下文是：

```text
当前 system / 工具定义
+ 有效用户要求
+ 当前必要 Note
+ 当前分支未完成 Todo
+ 下一动作所需证据
+ 按规则应交付的新输入
```

旧窗口完整 transcript、旧 Compaction 摘要和历史 Note 不自动搬入。原始记录仍可按权限查询。完整恢复工作集放不下时，保持旧窗口并报告无法提交，不截断任务清单或用户要求。

新用户消息在提交前到达时使相关 proposal 重新验证；提交后到达则按既有队列规则交付。硬切不消费 next-prompt 消息，不把一次模型请求重复投递。

崩溃恢复沿用现有语义：提交前仍用旧窗；已提交未发送则验证同一请求后发送；已 started 但无 finished 标为 outcome_unknown，禁止自动重放。进程恢复不重置维护额度。窗口次数仍沿用现有每个用户 prompt 至多 8 次，不新增一组循环上限。

## 6. 最短实施路径

| 修改位置 | 职责 |
| --- | --- |
| `packages/agent/src/agent-loop.ts` | 提供最终请求快照；完整工具批次后把维护控制交回宿主；不承载 Note/Todo 业务规则 |
| `core/context-budget.ts` | 统一工作、摘要、保存和恢复阶段的预算口径 |
| `core/agent-session.ts` + 新增包内 `core/context-maintenance.ts` | 将散落的自动触发收口为一个维护 Module；小 Interface 返回 continue/wait/blocked/cancelled，隐藏阶段和额度细节 |
| `core/compaction/compaction.ts` + `core/agent-session.ts` | 复用摘要生成；共享准备与提交操作校验候选请求，手动入口保留其用户操作能力 |
| `core/context-window.ts`、`core/session-manager.ts` | 同窗 Compaction 与真正 rollover 的身份语义；维护记录重建 |
| `core/context-rollover.ts` | 只接受模型换窗授权；绑定 Note/Todo 修订并复用提交、恢复、dispatch |
| `core/tools/context-note.ts`、`context-window.ts`、`todo-write.ts` | 复用现有模型工具；预算/阶段反馈、Note 校验、Todo 持久化顺序 |

请求准备钩子不能旁路修改 `agent.state.messages` 后继续发送旧的局部 AgentContext。压力守卫应交回明确的维护控制结果；宿主完成维护后重建上下文，废弃旧 PreparedAgentRequest，并对包含执行升级注入、扩展转换和队列预留的候选请求重新准备。提交及发送必须使用验证过的内容，测量过程不能消费队列。

交付顺序：先定义并验证同窗压缩与统一预算，再接入渐进调度，最后收紧模型换窗授权及 Note/Todo 恢复，完成端到端验收。属于同一目标实现，不长期并行运行两套自动策略。

实施时同步替换原来的“容量事件直接切窗”调用点及其专用类型、配置说明和测试。公开文档、CLI/RPC/Trace 对自动维护与任务完成的解释一起更新。历史用户日志不删除。手动 `/shake`、`/compact` 的操作能力保留；Compaction 窗口身份语义统一更新，不为旧自动架构加兼容分支。

## 7. 全链路验收

使用 suite harness 与 faux provider，检查实际 provider 请求、持久化记录、业务工具调用和重启重建，不能只测试状态枚举。

| 场景 | 必须验证的行为 |
| --- | --- |
| Shake 已解决压力 | 不调用摘要模型、不切窗，原始正文仍可合法回读 |
| Shake 不足、Compaction 有效 | 顺序正确，完整请求变小，windowId 不变，工具交互不拆分 |
| Compaction 后仍有压力 | 模型获得预算和选择机会；没有 new_context 就没有 rollover |
| 模型在自然断点主动换窗 | 不强制冗余摘要；同样经过保存、验证、提交和恢复 |
| 模型拒绝换窗或控制额度耗尽 | 不重复压缩、不超预算发业务请求、不伪装任务完成 |
| 超大输入/工具结果 | 所有维护请求自身合法；无法合法保存时旧窗口保留 |
| Note 与 Todo | Note 缺失/失效阻止提交；模型漏选的 pending Todo 仍在恢复集合；completed 不被恢复为 pending |
| 超过 8 个未完成 Todo | 从权威快照分页恢复全部任务，不受模型依赖列表上限截断 |
| Todo 写入失败 | 磁盘与内存保持同一旧状态，后续恢复和完成判断一致 |
| 并行工具、后台 Task、审批 | 完整结果落盘后才切窗，已完成工具不重复执行 |
| 新用户约束或 Todo 在准备时改变 | 旧 proposal 不提交；新约束及交付消息不丢失、不重复 |
| 新窗首个业务动作 | 所需用户要求、Note、Todo 已进入实际请求；从下一动作续跑 |
| commit/start/finish 各处中断 | 重建结果正确；未知执行结果不自动重放；额度不重置 |
| 模型已完成任务 | 不为减负再调用业务 continuation，不因陈旧 Todo 无限续跑 |

实现验收已运行相关定向测试与 `npm run check`。新增 `test/suite/progressive-context-memory.test.ts` 覆盖 Shake、同窗压缩、拒绝无净收益摘要、扩展 veto、无换窗意图、超大输入、重启额度、Todo 写盘失败和 12 项未完成 Todo 恢复。

最终一轮结果：coding-agent 的 10 个定向测试文件共 141 项通过、2 项真实 API 测试跳过；agent-core 的请求准备、append-only 与 Shake 测试共 63 项通过。另已通过队列、预算完整性、摘要完整性、Shake 重放、扩展和 RPC 相关回归。`npm run check` 与 `git diff --check` 通过；当前 npm 会对仓库已有 `min-release-age` 配置输出识别警告。

另用独立 CLI 进程的 RPC 接口模拟用户调用：用户要求记录 Todo、保存 Note 并换窗，再恢复要求/Note/Todo、写入 result.txt 并完成 Todo。实际执行了内置 write 工具，文件内容、一次换窗、Todo 完成状态及工具无错误均通过校验。

上述自动回归与 CLI/RPC 测试使用本地 faux provider，证明控制、持久化与续跑契约。另已通过源码 SDK 调用 `rrver/gpt-5.5`，覆盖真实摘要、模型换窗决策、Note/Todo 与实际文件写入；逐场景结果、发现的缺陷、修正与原始记录见 [真实模型验收报告](context-engineering-real-model-test-report.md)。这些有界场景不代替长期任务的大样本评估：约束遗漏、重复工作、未完成 Todo 覆盖、恢复输入量和成本仍需持续测量。
